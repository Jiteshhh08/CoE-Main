# API Architecture

## Overview

The CoE Portal uses a **Route Handler** architecture provided by Next.js App Router. Every file at `src/app/api/<group>/<name>/route.ts` automatically becomes an API endpoint.

## URL Structure

```
/api/<module>/<resource>/[id]/<action>
  │       │         │       │
  │       │         │       └── Specific action (e.g., confirm, register)
  │       │         └── Resource ID (dynamic parameter)
  │       └── Resource name (e.g., bookings, problems)
  └── All API routes
```

**Examples:**
- `POST /api/auth/login` — Login
- `GET /api/bookings/my` — My bookings
- `PATCH /api/admin/bookings/[id]/confirm` — Confirm a booking
- `POST /api/innovation/events/[id]/register` — Register for event

### HTTP Status Codes Used

| Code | When | Example |
|------|------|---------|
| **200** | Success | Login, fetch data |
| **201** | Created | Registration, new booking |
| **400** | Bad Request | Validation failed, invalid input |
| **401** | Unauthorized | No token, expired token |
| **403** | Forbidden | Wrong role, account pending/rejected |
| **404** | Not Found | Resource doesn't exist |
| **409** | Conflict | Duplicate email/UID |
| **429** | Too Many Requests | Rate limited |
| **500** | Server Error | Unexpected exception |

## Route Handler Pattern

Every API route file follows this structure:

```typescript
// src/app/api/<module>/<endpoint>/route.ts
import { NextRequest } from 'next/server';
import prisma from '@/lib/prisma';
import { successRes, errorRes, authenticate, authorize } from '@/lib/api-helpers';
import { someSchema } from '@/lib/validators';

export async function GET(req: NextRequest) {     // or POST, PATCH, DELETE
  try {
    // 1. Parse request body (POST/PATCH only)
    const body = await req.json();
    
    // 2. Validate with Zod
    const parsed = someSchema.safeParse(body);
    if (!parsed.success) {
      return errorRes('Validation failed', parsed.error.issues.map(e => e.message), 400);
    }
    
    // 3. Authenticate
    const user = authenticate(req);
    if (!user) return errorRes('Unauthorized', [], 401);
    
    // 4. Authorize
    if (!authorize(user, 'ADMIN', 'FACULTY')) return errorRes('Forbidden', [], 403);
    
    // 5. Business logic with Prisma
    const result = await prisma.someModel.findMany({ ... });
    
    // 6. Return success
    return successRes(result, 'Fetched successfully.');
  } catch (err) {
    console.error('Error:', err);
    return errorRes('Internal server error', [], 500);
  }
}
```

## Authentication & Authorization Layer

### `authenticate(req)` — Identity Verification

**File: `src/lib/api-helpers.ts` (line 37)**

```typescript
export const authenticate = (req: NextRequest): TokenPayload | null => {
  // Strategy 1: Bearer token in Authorization header
  const authHeader = req.headers.get('authorization');
  if (authHeader?.startsWith('Bearer ')) {
    const token = authHeader.split(' ')[1];
    return verifyAccessToken(token);
  }

  // Strategy 2: accessToken cookie
  const cookieToken = req.cookies.get('accessToken')?.value;
  if (!cookieToken) return null;
  return verifyAccessToken(cookieToken);
};
```

Returns `TokenPayload` or `null`. The route handler returns 401 if null.

### `authorize(user, ...roles)` — Permission Check

**File: `src/lib/api-helpers.ts` (line 60)**

```typescript
export const authorize = (user: TokenPayload, ...roles: string[]): boolean => {
  if (roles.includes(user.role)) return true;

  // Special: Industry membership is additive
  if (roles.includes('INDUSTRY_PARTNER') && typeof user.industryId === 'number') {
    return true;
  }

  return false;
};
```

### Common Authorization Patterns

```typescript
// Admin only
if (!authorize(user, 'ADMIN')) return errorRes('Forbidden', [], 403);

// Faculty or Admin
if (!authorize(user, 'FACULTY', 'ADMIN')) return errorRes('Forbidden', [], 403);

// Student only
if (!authorize(user, 'STUDENT')) return errorRes('Forbidden', [], 403);

// Any authenticated user (just check authenticate)
```

## Validation Layer

All input validation uses **Zod schemas** defined in `src/lib/validators.ts`.

### How Validation Works

```typescript
// 1. Define schema
export const bookingCreateSchema = z.object({
  purpose: z.string().min(5),
  date: z.string().refine((d) => !isNaN(Date.parse(d)), 'Invalid date'),
  timeSlot: z.string().min(1),
  facilities: z.array(z.string()),
  lab: z.string().min(1),
});

// 2. Use in route handler
const parsed = bookingCreateSchema.safeParse(body);
if (!parsed.success) {
  return errorRes('Validation failed', parsed.error.issues.map((e: any) => e.message), 400);
}
// parsed.data is now type-safe!
```

### Important: `safeParse` vs `parse`

- `safeParse()` — Returns `{ success: boolean, data?: T, error?: ZodError }`. NEVER throws.
- `parse()` — Returns the data or THROWS. Use `safeParse()` in routes.

## Error Handling Strategy

1. **All route handlers** wrap logic in try/catch
2. **Validation errors** → 400 with specific error messages
3. **Auth errors** → 401 (no token) or 403 (wrong role)
4. **Not found** → 404
5. **Business logic errors** → 400-409 depending on the error
6. **Unexpected errors** → 500 "Internal server error" (caught by catch block)
7. **Prisma errors** → Various codes (P2002 = unique constraint violation)

## CORS and Security Headers

- Cookies use `sameSite: 'lax'` — sent for same-site requests
- `secure` flag depends on `COOKIE_SECURE` env var
- Callback URLs are validated against allowed domains (`tcetcercd.in` and subdomains)
- The `pending_reg` cookie uses `sameSite: 'strict'` for extra security

## API Versioning

This project does NOT use URL-based API versioning (e.g., `/api/v1/`). All APIs are at `/api/<resource>/`. If breaking changes are needed, they would be managed through the Next.js deployment (blue-green) rather than URL versioning.
